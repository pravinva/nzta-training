Concepts & Terminology
What is Databricks
The Data Lakehouse Model
Databricks is a unified data and AI platform. It brings data storage, querying, engineering, machine learning, and governance into one place — running on your cloud infrastructure (Azure, in NZTA's case).
Data Warehouse
Structured, fast to query, designed for reporting. Rigid schema — expensive to change. Examples: SQL Server, Azure Synapse. Great for known, well-defined questions.
Data Lake
Raw files stored cheaply in cloud storage. Very flexible — any format, any structure. Without governance layers on top, it becomes difficult to manage and trust. Parquet is a common format here: a columnar file format that is compact and fast for analytics.
Data Lakehouse
Files stored cost-effectively in cloud storage, with warehouse-quality query performance, governance, and reliability layered on top. That's what Databricks delivers. Delta is the table format used in Databricks lakehouses, adding ACID transactions, version history (time travel), and reliable updates/deletes on top of Parquet files.
For NZTA: Your data — from road sensors, asset management systems, financial feeds, and external sources — lands in Databricks, gets processed into clean, trusted datasets, and is then available for analysis, reporting, and AI use cases.

Concepts & Terminology
Shared Language
Key Terms to Know
Workspace
Your organisation's instance of Databricks. The environment you log into — it contains all your data, code, and tools in one place.
Cluster
The computing engine that processes your code. Clusters start, run your job, and stop automatically. You don't manage the hardware.
SQL Warehouse
A cluster optimised specifically for running SQL queries and powering dashboards. This is what analysts connect to when running queries or using Genie.
Notebook
A document that combines code, explanations, and live output. Think of it as a living analysis document — part script, part report.
Catalog / Schema / Table
Three-level data hierarchy. Catalog = organisation-level container. Schema = topic area or domain. Table = the actual dataset you query.
Unity Catalog
The governance layer that controls who can access what data across the entire platform. Access control, lineage tracking, tagging, and auditing all live here.
Repos
Version-controlled code storage, connected to Git (Azure DevOps). Where data engineers keep and manage the code that builds your data pipelines.

Architecture
Data Architecture
Medallion Architecture
The Medallion Architecture is a layered approach to organising data. Each layer represents a different level of quality and readiness. Data moves from raw to refined as it passes through each stage.
Bronze
Raw • As-landed
Silver
Cleaned • Validated
Gold
Aggregated • Business-ready
🥉 Bronze — Raw Ingestion
Data lands here exactly as it came from the source — no transformations, no filtering. It's an audit log of what arrived. Preserving this layer means you always have a record to go back to.
🥈 Silver — Cleaned & Validated
Duplicate records removed, data types standardised, datasets joined across sources. This is the analytical base. Most data engineering work happens here.
🥇 Gold — Business-Ready
Business rules applied, metrics calculated, data aggregated for specific use cases. This layer powers dashboards, reports, and Genie. This is where analysts should start.
In the NZTA environment: Schema names include the layer as part of their name. You'll see patterns like procurement_silver → procurement_gold, or bronze_servicenow → gold_servicenow. The layer is embedded in the schema name — look for bronze, silver, or gold. The catalog dev_enterprise is the development environment; production data lives in a separate catalog.

Understanding Data Lineage

Every table has a Lineage tab in the Catalog. The example below is from your environment — the procurement domain, showing how contract data flows from Silver through to multiple Gold fact tables.

dev_enterprise.procurement_gold.dim_contract — Lineage view
Pipeline: The node between tables is the Azure Data Factory pipeline (dev-dlp-data-data-factory) that ran the transformation. Click it to see when it last ran and whether it succeeded.

Reading this lineage:

Upstream ←
procurement_silver.contract — the cleaned Silver table, with 25 columns including contract_id, contract_number, supplier_id, region_id.
This table
procurement_gold.dim_contract — the Gold dimension table with surrogate keys added, 23 columns, ready for reporting.
Downstream →
fact_ztl_evaluation, fact_key_result_area_outcome, fact_assessment — three fact tables that all depend on dim_contract for their contract dimension.
  • ↑
    Upstream — trace back to confirm the data origin and which source system it came from.
  • ↓
    Downstream — see which other tables and reports depend on this table. A data quality issue here affects everything downstream.
  • 👤
    Owner — visible in the Overview tab. The team responsible for this table and its pipeline.

Querying Data
SQL Editor & Notebooks
SQL Editor — Ad-hoc Queries
Open from the left nav. Select a SQL Warehouse from the dropdown at the top — this is the compute engine your query will run on. Write or paste a SQL query, then run it with Ctrl+Enter. Results appear immediately in the panel below.
-- Count contracts by type from Gold layer
SELECT contract_type,
       COUNT(*) AS total_contracts,
       project_manager
FROM dev_enterprise.procurement_gold.dim_contract
GROUP BY contract_type, project_manager
ORDER BY total_contracts DESC;

Queries can be saved, named, and shared with colleagues. Results can be exported to CSV or turned into a visualisation.

Notebooks — Structured Analysis
A notebook is a document made up of cells. Each cell contains either code (SQL or Python) or explanatory text. When you run a cell, the output appears directly below it — making notebooks both executable scripts and self-documenting analyses.
  • 📄
    Notebooks live in the Workspace section (personal work) or in Repos (version-controlled team code).
  • ▶
    Run a single cell with Shift+Enter, or run the full notebook from the toolbar.
  • 🔗
    Notebooks connect to a Cluster (not a SQL Warehouse). The cluster is selected at the top right — it may take a minute to start if it was idle.
  • 💾
    Notebooks auto-save. Sharing is done via the Share button — recipients open it in their browser, no download required.

Version-Controlled Code
Repos & Git Integration

Repos is where data engineers store and manage the code that builds your data pipelines. It's connected to Azure DevOps so that every change is tracked, reviewed, and deployed in a controlled way.

As a business user, you won't write code in Repos — but you'll hear engineers reference it constantly, and understanding what it is helps you follow those conversations.

What you can see in Repos
A folder structure of notebooks and scripts, organised by project or pipeline. You can open any notebook and read through it — the same notebook experience as the Workspace section, just version-controlled.

At the top of the screen you'll see a branch indicator — for example main or dev/feature-x. This tells you which version of the code you're looking at.

Terms you'll hear from engineers:

Branch
A parallel version of the code. Engineers work on branches so changes don't affect production until they're ready and reviewed.
Commit
Saving a set of changes to the repo with a description of what changed. Creates an audit trail of every modification.
Pull Request
A request to merge code from one branch into another — typically from a dev branch into main. Requires review and approval before changes go to production.
main / prod
The branch that reflects what's running in production. Engineers merge into main only when code is tested and approved.
In practice: When an engineer says "I'm raising a PR to push the new pipeline to prod," they mean they've written code in a dev branch, it's been reviewed, and they're requesting approval to merge it into the production codebase.

Pipelines & Monitoring
Workflows & Job Monitoring

Workflows is where scheduled and triggered data pipeline jobs are managed. When data in a table looks stale, incorrect, or missing, Workflows is the first place to check.

Jobs run automatically on a schedule — hourly, daily, or triggered by an event. Each run produces a log showing whether it succeeded or failed, and why.

  • 1
    Open Workflows from the left nav and select Job Runs.
  • 2
    Scan the run history. Green = success. Red = failed. A red run means the pipeline did not complete and downstream tables may not have refreshed.
  • 3
    Click a failed run to see the full error output. The error message describes what went wrong — a missing file, a source system issue, a schema change.
  • 4
    Identify the job owner from the job name, description, or tags. This is the person or team responsible for investigating and fixing the failure.
When data looks wrong in a report
Before raising a support request, check two things:

1. Workflows → Job Runs — did the pipeline that feeds this table run successfully? If not, when did it last succeed?

2. Catalog → Lineage — what pipeline feeds this table, and who owns it?

These two steps give you the information you need to raise a targeted, useful support request — or to confirm the issue is already being worked on.
Your role in monitoring: You don't need to fix pipeline failures. Your role is to notice when data doesn't look right, confirm whether a pipeline failure is the cause, and contact the right team with that context. That's significantly faster than a vague "the data looks wrong" ticket.

AI-Assisted Analysis
Genie — Ask Your Data Questions

Genie allows you to ask questions about your data in plain English. It interprets the question, generates a SQL query against your real data, runs it, and returns the result — along with a chart if appropriate.

Genie operates within a Genie Space — a pre-configured environment that's pointed at specific datasets and given context about what those datasets contain. Each Space is scoped to a domain.

Example questions to try
"How many assets are overdue for inspection in the Wellington region?"

"Break that down by asset type."

"Which region has the highest proportion of overdue assets?"

"Show me that as a bar chart."
  • 1
    Open a Genie Space from the left nav. Select the one relevant to your dataset or domain.
  • 2
    Type your question in plain English. Be specific — include filters like region, time period, or asset type to get a more precise answer.
  • 3
    Review the result. Click View SQL to see the exact query Genie ran. This lets you verify the logic and reuse the query in the SQL Editor if needed.
  • 4
    Refine with a follow-up. Genie maintains context across questions in a session — you can say "now filter that to the last 12 months" without repeating the full question.
  • 5
    Toggle between table and chart view. Pin useful answers or export the underlying data for use elsewhere.
Important: Genie queries your actual data — it does not generate or estimate answers. If it can't answer a question with the available data, it will tell you. The accuracy of its responses depends on how well the data and its columns are described in the Catalog.

How the Platform Fits Together
Each tool in Databricks has a defined role. Understanding how they connect means you know where to go for each task — and who to involve when something needs attention.

Engineers own the left side
Data engineers design and run the pipelines that move data from source systems through Bronze and Silver to Gold. They manage this via Workflows and Repos. When data doesn't look right, a pipeline failure is often the cause.
Unity Catalog is the contract
Everything in the Catalog is governed by Unity Catalog. Access control, data lineage, ownership, and tagging all live here. If you can see a table, you're authorised. Lineage connects the whole chain — from source to report.
You own the right side
Analysts and business users access Gold layer data via SQL Editor, Notebooks, and Genie. Results surface in Dashboards. Your starting point is always the Catalog — find the right table, check its lineage, then query it.
Next steps: Confirm your Microsoft SSO access is working. Identify one or two datasets relevant to your role. Raise any data access requests via the table owner shown in the Catalog. Your Genie Space will be configured for your domain — raise any questions with the data team.
